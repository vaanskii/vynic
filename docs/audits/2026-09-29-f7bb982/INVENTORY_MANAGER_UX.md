## მთავარი დასკვნა

დღევანდელი Inventory არის Cloud-ში წარმოებული მიღების, მომწოდებლის ანგარიშსწორებისა და გაყიდვიდან თეორიული ჩამოწერის რეესტრი. არსებობს პროდუქტები, ერთეულები, შეფუთვა, მომწოდებლის ასორტიმენტი, მიღების მონახაზი/გატარება/გაუქმება, ნაწილობრივი გადახდა, რეცეპტი, POS-ის გაყიდვის გაყინული შემადგენლობა და მოძრაობებით გამოთვლილი ნაშთი. მიღება და გადახდა ცალკე ფაქტებია, მიუხედავად იმისა, რომ საერთო ფორმა ორივეს შეყვანას ამარტივებს.

## 8. პრიორიტეტული სამუშაო და მიღების კრიტერიუმები

1. **საპილოტემდე — MGR-01/02/03/05, INV-03.** Venue-ს რეალური მაგიდები; POS-authoritative table/order ბრძანება; durable intent+outbox და retry identity; pending/completed UI; წაშლილ menu/recipe-სთან ისტორიული consumption-ის უსაფრთხო მიღება. მიღების პირობა: ორი განსხვავებული Venue layout; POS offline/queued/failed/succeeded; Cloud commit-ის შემდეგ ACK loss; invalid second order line არ ტოვებს ნაწილობრივ შეცვლილ mirror-ს; მენიუს წაშლის წინ დახურული offline Sale ერთი და მხოლოდ ერთი ჩამოწერით მიიღება.
2. **საპილოტეს მკაფიო საზღვარი — INV-01.** თუ რესტორანი მარაგების სრულ მართვას ითხოვს, locations, transfer, waste და stocktake blockers-ია. შეზღუდულ pilot-ში უნდა ეწეროს „მიღება/გადახდა/გაყიდვიდან თეორიული ხარჯვა“, სხვა პროცესები შეთანხმებულ გარე რეესტრში და reconciliation-ით. ეს პროდუქტის მფლობელის გადაწყვეტილებაა, არა ფუნქციის უკვე არსებობის მტკიცება.
3. **სანდო ყოველდღიური გამოყენება — MGR-04, INV-04.** ყველა რიცხვის წყარო/სიძველე; false empty-state-ის მოხსნა; stock/consumption სრული keyset ისტორია; გაუმართავი სინქრონიზაციის დასახელებული მიზეზი. მიღება: 101+ გაყიდვა ერთ დღეს სრულად იკითხება; Cloud reachable/POS offline მდგომარეობა აშკარაა; cache fallback არ ხდება fresh success.
4. **ფინანსური მოდულის გაფართოებამდე — MGR-06.** Payroll/obligation payment/reserve-ის დაკავშირებული reversal/correction workflow და არგუმენტირებული თარიღები; ერთჯერადი „გადახდილია“ entry-ის შეცდომა ისტორიას ვერ წაშლის. მიღება: იგივე reversal retry ერთხელ ითვლება; net outflow/debt/overpaid სწორია; cross-Venue უარყოფილია.
5. **შემდეგი Inventory ეტაპები.** ჯერ დოკუმენტზე მიბმული location ledger + transfer; მერე waste/internal; შემდეგ stocktake with trading cutoff; ამის შემდეგ PO/partial receipt/returns/credit allocation; ბოლოს production/yield და ისტორიული COGS/margin. ყველა ეტაპი ძველ movements-ს ინარჩუნებს და transaction/idempotency/tenant/late-event ტესტით იცავს საზღვარს.
